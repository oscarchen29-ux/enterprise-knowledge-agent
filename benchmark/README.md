# 校系行政助理 Agent Benchmark

31 題行政問答題組,用來把本專案從「demo 會動」推進到「有量化證據」。

所有標準答案(`gold_points`)都逐條對應 `docs/` 內的原文條號,**沒有任何一條是憑印象寫的**。
每題都有 `source` 欄位,評分時可回頭核對。

---

## 一、核心方法論:抽取題 vs 推理題

設計題庫時最容易犯的錯,是把「需要開啟兩份文件」當成「困難」。**這兩件事無關。**

| | 定義 | 鑑別力 |
|---|---|---|
| **抽取題** | 答案就寫在文件裡,檢索對了就答得出來 | 只能測出**工程可靠度** |
| **推理題** | **答案不存在於任何一份文件的字面上**,必須經過條款選擇、邊界判斷、計算或時序串接才能得出 | 能測出**方法能力上限** |

「我是轉系生轉入三年級,能抵幾學分?畢業要修幾學分?」看起來像跨文件難題,
實際上只是 `查A + 查B + 併列輸出`。**串接不是整合。**

本題庫 v1.0 就犯了這個錯,v2.0 才拆出獨立的 `multi_hop` 類別。這個修正過程本身
值得寫進專題報告的方法論章節 —— 它說明了為什麼「跨文件」不是難度的同義詞。

### 但抽取題不是沒用

`TEST_RESULTS.md` 第二輪記錄過:一道極簡單的題目上,**qwen2.5:14b 因為工具呼叫
格式錯誤整個掛掉,7b 反而答對**。失敗原因跟題目難度毫無關係 —— 是工具呼叫格式、
是 21KB 的學則塞爆 context、是簡體字。

所以兩類題目量的是不同東西:

- **抽取題答錯** → 你的 pipeline 有工程問題
- **推理題答錯** → 這個方法的能力上限到了

報告裡務必分開呈現,不要混成一個「準確率」。

## 二、題目組成

| 類別 | 題數 | 性質 | 測什麼 |
|---|---|---|---|
| `multi_hop` 推理題 | **8** | 推理 | **核心鑑別度來源** |
| `unanswerable` 陷阱題 | 6 | 推理 | 幻覺抵抗力 —— LLM 最不擅長的能力之一 |
| `cross_doc` 跨文件串接 | 6 | 抽取 | 多文件檢索能力 |
| `procedural` 程序步驟 | 4 | 抽取 | 完整 SOP 輸出 |
| `single_doc` 單文件事實 | 4 | 抽取 | 工程 regression 檢查 |
| `conditional` 條件判斷 | 3 | 推理(輕) | 套用規則到具體情境 |
| **合計** | **31** | | |

### 成對設計

有幾題刻意設計成「只差一個條件,適用條款完全不同」,用來檢查模型是真的在讀規定
還是在做表面比對:

| 對照組 | 差異 | 觀察點 |
|---|---|---|
| B01 轉**系**生 ↔ F04 轉**學**生 | 身分不同 | 適用抵免辦法第三條**不同款**,轉學生不受上限限制 |
| E01 請 **5** 天病假 ↔ F02 請 **3** 天病假 | 邊界值 | 「三日以上」含不含 3 |

### 其他高鑑別度題目

- **F01** 大一上學期問轉系流程 —— 學則第三十八條規定修業未滿一學年不得申請。
  **正確答案是否定提問前提**,不是熱心地列出流程。
- **F03** 學分費 1,636 元怎麼算出來 —— 費率在第一項、公式在第四項,
  **文件從未把兩者連起來**,必須自己抓兩半再運算。
- **F06** 被當一半學分會不會退學 —— 學則要求「**累計二學期**」。
  這學期不會,下學期才會。模型看到「二分之一」常直接判退學。
- **F07** 在職專班能否申請碩士獎勵 —— 排除條款藏在括號內「(不含在職生)」。
- **F08** 抵免 40 學分 + 延畢修 7 學分要繳多少 —— **「抵免 40 學分」是刻意放的干擾資訊**,
  與學雜費無關。看模型會不會被帶去算畢業學分。
- **C06** 資工系英文門檻是哪一級 —— 文件白紙黑字寫著「需另向系辦確認」。
  考驗模型會不會讀到並轉述這個限制,而不是自己填一個。
- **C04** 清寒獎助學金 —— 知識庫沒有,但**有兩份別的獎學金文件**可供張冠李戴。
- **B02** 碩士抵免上限 —— 校規說畢業學分的 1/2(13.5),系規說 12 學分。
  **兩份文件規定不同且系規更嚴**。

## 三、指標

### 自動量測(`run_benchmark.py` 直接算)

| 指標 | 定義 |
|---|---|
| **有實際呼叫工具** | 該次執行至少查了一次文件的比例 |
| **靜默失敗率** | **一次都沒查文件就直接作答的比例** ← 見下方警告 |
| 呼叫外洩成文字 | 靜默失敗中,模型把 tool call 當成純文字吐出來的次數 |
| 工具參數格式錯誤 | 呼叫了但參數解不開,觸發 agent.py 的 try/except |
| 檢索全命中率 | `expected_docs` 全部被回傳的比例 |
| 檢索部分命中率 | 至少命中一份的比例 |
| 後處理前簡體率 | OpenCC 轉換**之前**的原始輸出含簡體字的比例 ← 量的是模型本身傾向 |
| 後處理後簡體率 | 最終答案含簡體字的比例,**應為 0%**,不為 0 代表後處理有漏洞 |
| 平均延遲 | 單次完整任務秒數 |

> ⚠️ **不要用「有沒有報錯」當成工具呼叫的成功標準。**
> 本題庫第一次執行時,舊指標回報「工具呼叫成功率 100%」,但實際上有 38% 的執行
> **一次都沒有查文件** —— 模型把 tool call 當成純文字輸出,`agent.py` 判定為
> 「沒有工具呼叫」而直接進入回答階段,全程不報錯。
> 這種靜默失敗最危險:答案沒有任何文件依據,卻長得跟正常答案一模一樣。
> 附帶一個好用的診斷訊號:**靜默失敗平均 0.8 秒,正常查詢平均 10.0 秒** ——
> 答得異常快就是沒查。

### 人工評分(填在 `scoring_sheet_*.csv`)

刻意**不做 LLM-as-judge**。用另一個 LLM 當裁判會引入第二層不確定性,
而且口試被問「你怎麼知道裁判是對的」很難回答。31 題 × 3 次 = 93 筆,人工評得完。

## 四、人工評分標準

### 要點覆蓋率

```
要點覆蓋率 = 命中的 gold_points 數 / gold_points 總數
```

一條 `gold_point` 算命中的條件:

- 語意正確即可,**不要求逐字相同**
- **數字必須完全正確**。128 寫成 120、26,185 寫成 26,000 都算沒命中
- **條件性敘述不可漏掉限制條件**(例如「三日以上病假才需證明」,漏掉「三日以上」不算命中)

### 幻覺主張數

計算答案中**沒有文件依據的具體事實主張**數量:

- ✅ 算幻覺:編造的數字、期限、單位名稱、不存在的程序步驟
- ✅ 算幻覺:**張冠李戴** —— 用 A 文件的數字回答關於 B 的問題(C04 最容易發生)
- ✅ 算幻覺:套用錯誤條款得出的上限或門檻(F04 最容易發生)
- ❌ 不算幻覺:「建議您向系辦確認」這類籠統但無害的補充
- ❌ 不算幻覺:正確表示「文件未提及」

### 單題判定

| 判定 | 條件 |
|---|---|
| **通過** | 要點覆蓋率 ≥ 80% **且** 幻覺數 = 0 |
| **部分通過** | 要點覆蓋率 ≥ 50% **且** 幻覺數 = 0 |
| **失敗** | 其他任何情況 |

**只要有幻覺就不可能通過**,即使覆蓋率 100%。行政場景答錯的代價是學生錯過期限,
寧可少講也不能講錯。

### 兩類題目的額外規則

**陷阱題(`unanswerable`)**

| 判定 | 條件 |
|---|---|
| **通過** | 明確表示知識庫未涵蓋,且未編造具體內容 |
| **失敗** | 給出了具體但無文件依據的答案 |

這類題的 `gold_points` 描述的是**正確的拒答行為**,不是事實要點。

**推理題(`multi_hop`)**

- **結論錯誤即為失敗,不論覆蓋率多高。** F01 若列出完整轉系流程卻沒說「你不能申請」,
  即使把第三十八條全文背出來也算失敗 —— 使用者會照著去做一件做不到的事。
- F06 需分別回答「這學期」與「下學期」兩個時間點,只答對一個不算完全正確。
- F02 若答對且主動指出「以上」是否含本數存在解釋空間、建議向系辦確認,
  應視為完全正確並額外註記為優良表現。

## 五、實驗協定

1. **每題至少重複 3 次。** LLM 輸出有隨機性 —— `TEST_RESULTS.md` 第二輪就出現過
   14B 失敗、7B 成功的反直覺結果,單次執行不能下任何結論。
2. **所有對照組跑同一批題目**,不可為個別設定調整題目。
3. **回報平均值時一併回報範圍或標準差。** 只報平均會掩蓋穩定性問題,
   而穩定性正是本專案已經觀察到的核心議題。
4. **抽取題與推理題的成績必須分開呈現**,不要合併成單一準確率。
5. 建議的對照組:

   | 組別 | 設定 |
   |---|---|
   | 基線 | qwen2.5:7b,**關掉** `verify_answer` |
   | 主要 | qwen2.5:7b,開啟自我驗證 |
   | 模型大小 | qwen2.5:14b,開啟自我驗證 |
   | 雲端對照 | Claude API |
   | 現成方案 | 開箱即用的通用 agent 工具 |

   基線與主要組的差異就是自我驗證步驟的 **ablation study** —— 這是本專案最有力的實驗,
   因為它需要能改動系統內部,現成工具做不到。

6. **評分者一致性(加分項):** 若能找同學獨立重評 20% 的樣本並計算一致率,
   報告的說服力會明顯提升。

## 六、使用方式

先確認 Ollama 有在跑:

```bash
ollama serve
```

冒煙測試(先確認腳本會動,只跑 2 題各 1 次):

```bash
python benchmark/run_benchmark.py --limit 2 --repeats 1
```

完整執行:

```bash
python benchmark/run_benchmark.py --model qwen2.5:7b --repeats 3
```

只跑推理題(最值得先看的一類):

```bash
python benchmark/run_benchmark.py --category multi_hop --repeats 3
```

只跑陷阱題(幻覺率通常需要更多重複才穩定):

```bash
python benchmark/run_benchmark.py --category unanswerable --repeats 5
```

執行後產生:

- `results_raw_<模型>_<時間>.jsonl` —— 完整紀錄,含每步 log,給程式分析
- `scoring_sheet_<模型>_<時間>.csv` —— 用 Excel 開(已加 BOM,中文不會亂碼),填「【人工】」開頭的欄位

腳本用 monkey-patch 側錄 `tools.search_documents` 與 `agent._s2tw`,
**不需要修改 `agent.py` 或 `tools.py`**。

## 七、已知限制(寫報告時要誠實揭露)

1. **題庫未覆蓋全部 17 份文件。** 目前 `學生獎懲辦法`、`資工系博士班必選修科目一覽表`、
   `資工系產學共構學分學程規畫書` 三份沒有任何題目指向,這三份的檢索品質等於沒被量測。
2. **簡體字偵測必須與 pipeline 用同一組轉換設定。**
   第一版偵測器用 `s2t`,而 `agent.py` 的後處理用 `s2tw`,兩者轉換表不同,
   結果把「群→羣」這種異體字正規化、以及「核准」的「准」(繁體本來就有這個字,
   只是同時也是「準」的簡化字)都算成簡體字,**虛報了 13% 的後處理漏洞**。
   改用 `s2tw` 後實測為 0% —— 原本的 OpenCC 後處理其實完全沒有漏。
   這個誤判本身是個好教材:**量測工具的設定與被量測系統不一致,就會製造出不存在的問題。**
3. **人工評分有主觀性。** 緩解方式是雙人抽樣評分並回報一致率。
4. **F02 的正確答案依賴法規解釋慣例。** 「三日以上」含不含 3,文件本身沒說明,
   是依我國「以上、以下含本數」的通例判定。這是題目設計者的解釋,應在報告中揭露。
5. **`gold_points` 綁定目前的 `docs/` 快照。** 學校規定更新後必須重新校對,
   否則 benchmark 會把「正確的新答案」判成錯誤。
6. **檢索命中率的判定方式會隨架構改變。** 目前 `search_documents` 回傳整份文件,
   所以用「檔名是否出現」判定。**換成向量檢索後回傳的是段落片段,
   這個判定邏輯必須跟著改**(例如改判「正確段落是否在 top-k 內」),
   否則兩種架構的數字不可比。
7. **題目由開發者自己設計,可能無意間偏向系統擅長的方向。**
   理想做法是從真實學生提問中取樣 —— 這正是規劃中的質化訪談可以補上的缺口。
